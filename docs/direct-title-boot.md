# Direct TITLE Phase 4: first real execution harness

Opt-in. Nothing here changes the default generator, discovery, closure or Phase 3 outputs (`--probe`, `--boot-bios`, `--boot-isa` and
`--noreturn` / `--callback-set` are all off by default). No proprietary file or proprietary-derived blob is committed: the EXE and the
TITLE image are read-only external inputs and everything generated stays under the ignored `build/generated/direct-title-boot/`.

## Result

**REAL HARNESS RUNS, BLOCKED BEFORE TITLE HANDOFF.**

> **Phase 5 update (`docs/direct-title-libcard.md`):** with the opt-in `--boot-card` variant `B0:0x4a` is closed as a state-only boundary and the
> boot advances to the libcard kernel-patch routine `0x8005a920` (step 339,099). The Phase 4 result below is unchanged and still pinned by the default
> (`discovery.boot`) run.

The harness boots the real `SLES_017.26` through the true PS-X EXE entry, executes 338,917 guest instructions of the PAL's own startup
(BSS clear, InitHeap, engine init, ResetGraph, ResetCallback, GPU/DMA/SPU setup, VSync wait), delivers one VBlank interrupt through the
PAL's own interrupt machinery, and then stops, deterministically, at the **first unsupported boundary**:

> `B0:0x4a` (kernel function table B0, entry 0x4a; PsyQ name `InitCARD`) called from libcard `0x8005a2c4` at `0x8005a308`
> (`jal 0x8005a814`, the BIOS thunk `addiu t2,zero,0xb0; jr t2; addiu t1,zero,0x4a`), `a0 = 0`.
> Call chain: `0x80014a08` → `0x80016414` (main) → `0x80044d8c` (engine init) → `0x8003ffe0` → `0x8005a264` → `0x8005a2c4` → `0x8005a814`.
> Stop type: `ungenerated-function` (`no-proven-path-to-return`, `bios-call-boundary`), at step 338,917, `ra=0x8005a30c`, `sp=0x801fff50`.

Why this is a real boundary and not something to paper over: the libcard code that runs after this call reads and patches kernel RAM
(it addresses the kernel at `0xdf80` / `0xa001dfac`) and fetches the kernel tables through `B0:0x56/0x57`. Any behaviour for `B0:0x4a`
would be an invented kernel memory image, which the phase rules forbid. It needs its own phase (see "Secondary blockers").

## True boot entry and startup chain

PS-X EXE header (parsed by `boot::parsePsxExe`, not assumed): initial PC `0x80014a08`, GP `0`, load address `0x80014a00`, text size
`0x55000`, stack base `0x801ffff0` (offset 0). The initial PC is **outside** the 44-function Phase 3 registry (that registry's roots are
7 library entry points, none of which is the program entry), so a separate boot unit is generated from the same closure infrastructure.

1. `0x80014a08` startup stub (generated, not faked): zero-fills BSS `0x80069390..0x800768f0` (~68k instructions), sets `sp=0x80200000`,
   `gp=0x80069368`.
2. `jal 0x8004e5f4`: `A0:0x39` InitHeap(`0x800768f4`, `0x181710`) (thunk).
3. `jal 0x80016414` main; the stub ends in `break 1` (never reached; a registered `--noreturn` root).
4. main calls `0x80014a00` (a `jr ra` stub), then `0x80044d8c` (engine init), `0x80044ea0`, `0x80015ec0`, `0x80040ef4`, `0x80016118`,
   `0x8004447c`, then a retry loop around the loader `0x800415e0`.
5. `0x80044d8c` calls, in order: FlushCache (`0x8004e604`, `A0:0x44`), ResetGraph `0x80051604`, `0x80051778`, SPU init `0x8003ed8c`, pad/card
   init `0x8003ffe0` → `0x8005a264` → libcard `0x8005a2c4`, CD init `0x80046468` / `0x80046680`, `0x8004f6ec` (COP0/GTE init).

The run stops inside step 5 at the libcard call.

## The harness (`tests/direct_title_boot.cpp`, opt-in)

`DirectTitleBoot EXE MAP [--budget N] [--call-budget N] [--trace FILE] [--stop PC]...`

Setup, in order: allocate `Context` (2 MiB guest RAM) → `loadExe` copies the text segment to `0x80014a00` → `applyBootState`:
`pc = header PC`, `sp = fp = header stack`, `gp = header GP`, `ra = hostReturn (0x80)`, every other register 0 → install `BootDevice`,
`bootPolicy`, `bootSyscall`, `Hardware` (MMIO), `Probe`, `InterruptEntry` → `runBoot(executeDirectTitle, pc, budget)`.
Nothing seeds a runtime cell: all cells the Phase 3 report listed (`M[0x80067d70/78]`, the callback root `M[0x80061a0c]`, the interrupt
buffers) are written by the PAL's own init functions during the run, which is itself checked by the trace (`B0:0x19` registers the PAL's
own `jmp_buf`).

Exit code: `0` stop requested or clean return to the host; `2` explicit unsupported boundary or exhausted budget (never silent);
`1` harness error. Failure diagnostics: guest PC, containing generated function (or boundary stub) range, boundary type, all GPRs, hi/lo,
pending load, MMIO address/width/value for device faults, call depth, remaining budget, and the BIOS call log.

The trace (`--trace`) is low-noise: one line per checkpoint (EXE entry, first entry of every generated function, BIOS calls, MMIO
configuration events capped at 12 per register, GP1 commands, SPU RAM transfers, IRQ entry/return, the final stop), never per
instruction. The time base is the guest instruction count only, so two runs are byte-identical (checked by `x_boot` / the PowerShell script).

## Interrupts: the PAL's own mechanism, entered by the host

The PAL's ResetCallback (`0x8004dc84`) does `setjmp` into the buffer `0x800609bc` (return address `0x8004dcec`), overwrites `buf.sp` with the
interrupt stack `0x8006199c` and registers the buffer with `B0:0x19` (`SetCustomExitFromException`). The code at the `setjmp` return point is
`beq v0,zero,+3; nop; jal 0x8004dd60` — the PAL's ISR — which ends in `B0:0x17` (`ReturnFromException`). The host plays the kernel's role and
nothing more: when all conditions hold the interrupt is *taken* as a `longjmp(buf, 1)` into that buffer.

Entry conditions (`boot::InterruptEntry::poll`, all required): a custom exit is registered; `irqEnabled` (the PAL ran `ExitCriticalSection`,
`syscall` with `a0 = 2`); not already inside an ISR; `I_STAT & I_MASK != 0`; the pc is not a delay slot; there is no pending load. Entry loads
`ra/sp/fp/s0..s7/gp` from the buffer, sets `v0 = 1` and redirects to the buffer's `ra` (which must be inside a generated function); the
interrupted frame (32 GPRs, hi, lo, pc, irq state) is saved and restored by `B0:0x17`. In the real run: `irq-enter #1` at step 338,689
(`istat=1`, `imask=9`, interrupted `0x8004da78`, in the VSync wait), the PAL's ISR `0x8004e254` increments `M[0x80061a40]`, `irq-return` at
338,861.

## Host clock policy (explicit, not hardware evidence)

One guest instruction = 2 CPU cycles; a video field = 677,376 cycles (50 Hz at 33.8688 MHz); a scanline = 2,168 cycles. VBlank edge *n* occurs at
cycle *n* × 677,376 (the first at step 338,688). The edge latches `I_STAT` bit 0 regardless of `I_MASK` and stays until the PAL acknowledges it.
`M[0x80061a40]` (the VBlank counter) is **never** written by the host: it is changed only by the PAL's own ISR (`0x8004e254`). The constants decide
*when*, never *what*: the PAL only observes differences of root counter 1 and the VBlank edge.

## BIOS / kernel set (`src/bios_table.hpp`, `src/bios_boot.hpp`)

Implemented with exactly the semantics the PAL call sites observe: `A0:39` InitHeap (recorded), `A0:44` FlushCache (counted, no I-cache), `A0:49`
GPU_cw (a GP0 bus write, so the GPU model decides), `A0:72` CdRemove (counted), `B0:07/08/0a/0b/0c` events (mode `0x2000`, no handler; WaitEvent only
completes for a delivered event, otherwise fatal), `B0:17` ReturnFromException, `B0:19` SetCustomExitFromException, plus the three Phase 3
functions (`B0:35`, `B0:5b`, `C0:0a`). `SYSCALL` code 0 with `a0 = 1/2` is Enter/ExitCriticalSection. Every other `(table, function)` pair is a
fatal "kernel function is not implemented" with its call site — including the stop point `B0:4a`.

## TITLE compatibility (`tools/recomp/title_compat_main.cpp`, `DirectTitleCompat EXE TITLE [MAP]`)

Deterministic static walk of the real TITLE type-2 image (base `0x80010200`, size `0x42b4`) from its 5 public entries over the live code
`[0x80010204, 0x80012b54)` (2,484 reachable instruction states, delay slots handled): 140 `jal`, 42 `j`, 223 branches, 33 `jr ra`, 4 bounded
jump tables (all 4 reached), 346 COP2/GTE words, 1 `break`, **no `jalr`, no J/JAL target outside the image**. So the TITLE unit calls **no** EXE
entry: in-44-registry 0, existing HLE 0, dynamic/static-table 0, missing-but-provable 0, unknown-blocking 0. It needs only EXE *data* through the
27-slot import table at `0x8006b340` (every populated slot points into EXE BSS/data; the table itself is written by the guest load path
`0x80041c54` region / `0x80044c30`, not by the TITLE image). The bounded coverage need against the 44-entry registry is therefore empty; what is
missing for the handoff is the load path (below), not registry entries. On Windows the report additionally recognizes the image by masked SHA-1.

## CD / libcd

Not reached. The run stops before the PAL's CD init (`0x80046468` / `0x80046680`, generated) executes, so none of the existing CD backing, libcd HLE,
pump, guest read callback or ring/BZZ infrastructure is engaged yet and nothing was duplicated. The loader `0x800415e0` (the owner of the TITLE load)
is an unreached boundary stub (flow crosses the entry/analysis bound).

## Boundary ledger

First (blocking): `B0:0x4a` at `0x8005a814` as above. Secondary, found statically in the same unit and not reached:
`0x8004f6ec` (COP0/GTE init, "coprocessor-control-or-operation"), the CD controller registers (CD init is generated but `0x1f801800..` is unmodelled),
the loader `0x800415e0`, `0x80019364`, `0x80016218` (direct call outside the payload), GTE-containing functions (`0x800353a4` etc., COP2), SYSCALL/COP0 words
in unrelated library code, and the IRQ-callback stubs `0x80048f50`, `0x80048cdc`, `0x8004a078`.
